# 扩展 S3 同步内容

同步协议当前为版本 6。版本 5 开始携带已删除书籍的批注展示资料（书名、封面和更新时间）；版本 6 改用密钥派生的对象名与 `LIBZORA-SYNC3` 长度补齐封装，并在自备加密存储的快照中保存 `BlobNamingSalts`。旧客户端不能安全下载或维护这些对象，遇到最低读取协议高于自身能力的快照必须在上传和清理之前中止；各设备应一起升级。后续兼容性新增保持协议 6，规则见[快照兼容约定](s3-snapshot-compatibility.md)。

## 同步时序：混合逻辑时钟

每个跨设备可写的行和删除标记都可携带可选的 `syncVersion`，格式为
`物理时间(19 位 UTC ticks):计数器(10 位):设备 ID`，按固定宽度字符串即可比较先后。
它表示“这一行在因果顺序中的位置”，与业务时间戳分工如下：

- `updatedAt`、`createdAt`、`modifiedAt`、`deletedAt` 仍是业务时间，也是旧客户端唯一的排序依据，不能删除或改写语义。
- 新客户端在捕获、字段合并和删除时分配 `syncVersion`；与上一份基线相比没有变化的行继续复用原版本，只有真正改动或被合并写入的行才取得新版本。
- 生成本地修改前，设备先读取所有远端快照的 `syncVersion` 并推进本机时钟，因此“看到远端修改后再改”一定排在远端修改之后，即使本机时钟偏慢或快照晚到。
- 整行应用按版本比较；版本相同再比较行时间，最后按序列化内容排序，保证所有设备选出同一行。删除标记与存活行版本相同时删除获胜；存活行版本更新则视为本地恢复，删除标记被抵消。
- 旧客户端不认识 `syncVersion` 时会把它当作未知字段原样保留，继续按时间戳合并。新客户端遇到没有版本的行（旧快照或手工数据）时，用双方的行时间比较，并让有版本的一方在时间相同时获胜。
- 阅读布局的“排版网格”和“外观配置”分别使用 `layoutPartVersion` 与 `profilePartVersion`，避免一台设备改字号、另一台改主题时互相覆盖；旧客户端只看到两个 `UpdatedAt`，仍按旧方式合并。

混合逻辑时钟保证因果顺序与最终收敛：任一设备看到其他设备的修改后，其后续修改一定排在后面。它不能替用户判断两台设备完全离线、互未观察时“现实世界中谁最后下手”；这种情况按上述确定性规则收敛，而不是按直觉猜测。需要精确“最后编辑时间”的场景应改为在线编辑或使用可信时间源，无需依赖墙钟排序。

## 已有实体的字段合并

快照以“整行最后写入者获胜”为默认规则，但批注和书籍以本设备上一次成功上传的快照为共同祖先，对本设备和**所有远端设备**的同一行做字段级合并（N 路，而不是先按时间折叠成一行）：

- 本地和远端只改动不同字段时，两边修改都保留；共同祖先中未改动的字段不参与覆盖。
- 批注分成锚点（章节、片段、起止偏移、选中文本、前后文）、颜色、下划线样式和笔记四组，颜色与下划线是独立字段，不能捆绑。
- 书籍的每个元数据字段（书名、作者、丛书、简介、出版信息、标签、分类、收藏和阅读状态等）分别合并，不再把“标签/分类”或“收藏/阅读状态”当成一个整体。封面二进制仍按封面哈希单独合并。
- 多台设备同时修改同一字段时，`syncVersion` 较晚者获胜；旧快照没有版本时按行时间比较；版本和时间都相同但内容不同时，按序列化内容排序选出同一结果，所有设备因此收敛。合并出的新行取得一个新的版本，表示这次合并事件。
- 同一段文字在两个设备上各自新建批注时，如果书、文件、章节、位置和选中文本一致，合并为一条，保留较早创建的 ID，笔记用空行拼接，失败的 ID 写入删除记录。书签只有位置、标题和引文都相同才视为重复，避免误删用户有意保留的同位置书签。
- 本地 SQLite 的 `julianday()` 只有约 0.1 毫秒分辨率，因此字段合并产生的新版本至少比旧版本晚 1 毫秒，不能用 1 tick 递增。

## 后续新增同步实体

新增**带独立字段**的同步实体时：

1. 在 `S3SyncSnapshotModels.cs` 声明可移植的快照类型和集合。本机路径、凭据等不能序列化。
2. 在 `S3SyncService.EntityRegistry.cs` 注册集合、稳定主键、版本、删除覆盖规则及对象哈希。注册表统一用于版本索引、删除推断、未修改行识别、旧快照清理保护和对象引用收集。集合覆盖测试会检查漏注册。
3. 为实体实现事务内完整和增量捕获，并在合并事务中实现领域规则。身份映射、阅读数据重置代次、外键依赖等仍需要明确处理，不能只注册集合就开始同步。
4. 如果需要外部对象，在事务外校验并下载，在数据库事务内保存引用。对象缺失或损坏时不要推进对应资料的版本，以便下次重试。上传也必须在快照上传之前完成。
5. 明确删除策略。批注仅由自身删除记录覆盖；书籍删除不能代替批注删除。随批注派生的展示资料不通过集合缺失推断删除，避免仅删除书籍便丢失封面。
6. 增加双向、多设备、离线旧版本、重复同步、删除与保留、对象故障和清理测试。变更会影响旧客户端合并或清理安全时，提高协议版本，并验证拒绝新版快照期间远端无写入或删除。

### 可累加数据：以听书时长为例

听书时长、朗读字数等“每台设备各自累加”的数据不能使用普通整行 LWW，否则一台设备会覆盖另一台设备的累计值。推荐结构：

```json
{
  "version": 6,
  "listeningTime": [
    { "id": "<deviceId:N>", "updatedAt": "2026-11-12T08:00:00+00:00", "seconds": 3600 }
  ]
}
```

规则：

- 每台设备只写自己的行，`id` 使用稳定的设备标识，`updatedAt` 是该设备最后写入时间，`seconds` 是该设备的累计值。
- 合并时按 `id` 取并集，同一设备取 `updatedAt` 较新的行；总时长由客户端读取时求和，不在快照里写全局总数。这样重复合并、旧快照晚到都不会翻倍或回退。
- 如果新字段在旧客户端上还不存在，应放在实体或快照的 `[JsonExtensionData]` 中；旧客户端会原样保留。新客户端定义好 `id` 和 `updatedAt` 后，旧客户端也会按行合并，而不是用整个数组覆盖。
- 只有无法提供稳定行标识或时间戳的未知数组才整体保留。不要把需要按行合并的数据塞进普通字符串或对象，否则旧客户端只能整块覆盖。
- 正式增加类型化集合时，仍要在 `SyncEntities` 注册；注册后走类型化捕获、应用和删除逻辑，不再依赖不透明数组合并。

展示资料按 `UpdatedAt` 合并；相同版本依次按书名和封面内容哈希的序数排序确定结果。时间比较保留完整精度。资料、批注和删除记录在同一 SQLite 事务中捕获，封面哈希和网络操作在事务外处理。
